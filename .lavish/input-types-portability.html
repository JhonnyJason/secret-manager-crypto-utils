Input types × runtimes: who owns which divergence

Rule: different error types on different runtimes are fine. Success on one runtime and failure (or a different result) on another is a bug - unless it is a known runtime bug that will be fixed soon, or the fix would cost every other runtime too much.

How it was measured (11 configurations)

One probe (scratchpad/zz-probe.mjs, not in the repo) ran every byte argument of every API function with 11 input flavors, plus thingy-byte-utils directly. For each call: same result as a plain Uint8Array? error type? was the caller's input changed?

node 26.12, bun 1.4.4, deno - each native and with native Ed25519/X25519 hidden (·fb = noble fallback). Chromium 156, Firefox 159, WebKitGTK 60.5 headless (no Buffer, no SharedArrayBuffer: not cross-origin isolated). JS-hex = node with toHex/fromHex/setFromHex deleted (what runtimes without native hex take, likely node 22 - not verified on a real node 22). no-TextEnc = additionally no TextEncoder/TextDecoder/isWellFormed (minimal runtimes).

Old-code Firefox: resizable flavors left out - they froze the tab (finding S5).

Findings and ownership

Owner: smcu this package · tbut thingy-byte-utils · runtime a runtime bug. Pick a disposition per row, then queue once at the bottom.

S1 smcu portability fixed

Resizable views: WebCrypto accepts on node/deno, rejects on bun + all browsers

Runtimes: node, deno ✔ · bun, Chromium, WebKit, Firefox ✘
sha*, symmetric key/gibbrish, asymmetric secretKey/encryptedContent, DH secretKey. Spec (WebIDL BufferSource without [AllowResizable]) says reject - node/deno are the lenient ones. Fixed by copying caller bytes into a plain Uint8Array on entry.
S2 smcu portability fixed

SharedArrayBuffer views: WebCrypto rejects on node/bun, accepts on deno; noble paths accept everywhere

Runtimes: deno ✔ · node, bun ✘ (browsers: no SAB without cross-origin isolation)
symmetricEncrypt/Decrypt key: deno success, node/bun failure. Same copy fixes it.
S3 smcu portability fixed

verifySignature answer depends on buffer flavor and native vs fallback path

Runtimes: resizable: bun/Chromium/WebKit 'Malformed input!', others valid · shared: native 'Malformed', fallback valid
Fails closed, but a valid signature must verify everywhere. Same copy fixes it.
S4 smcu side effect fixed

Fallback verify reversed the caller's Buffer signature in place

Runtimes: every runtime on the noble fallback path (+ browser bundles with a Buffer polyfill)
bytesToNumberLE did bytes.slice().reverse(); Buffer.prototype.slice is a view, not a copy. Unreachable now: internal arrays are always our own plain copies.
S5 runtime runtime bug avoided

Firefox: subtle.importKey with a resizable view freezes the tab

Runtimes: Firefox 159 only - digest/encrypt correctly throw TypeError instead
Verified in isolation (AES-GCM raw, Ed25519 raw, X25519 raw). Old code reached it via symmetricEncrypt(key) and verifySignature(publicKey). Now unreachable: importKey only ever sees our copies. Worth a Firefox bug report.
S6 smcu consistency fixed

shas accepted ArrayBuffer / DataView / Uint8ClampedArray, everything else rejected them

Runtimes: uniform
Not a portability issue, but contradicted README/.d.ts. Now TypeError like every other byte argument.
T1 tbut portability open

hexToBytes(non-string): native path TypeError, JS path returns empty Uint8Array

Runtimes: native fromHex ✘(TypeError) · JS path (node < 25?, older browsers) ✔ silently
hex.length is undefined → odd-length check passes, n = 0 → empty result. smcu is insulated: its wrapper checks typeof string first.
T2 tbut portability open

bytesToHex(detached array): native toHex throws TypeError, JS path returns ""

Runtimes: native toHex ✘ · JS path ✔ silently
smcu insulated: caller arrays are copied (new Uint8Array(detached) throws) before tbut sees them.
T3 tbut portability open

utf8ToBytes(non-string) without TextEncoder + isWellFormed returns empty bytes

Runtimes: minimal runtimes only · everywhere else TypeError
Only in runtimes lacking TextEncoder and String.prototype.isWellFormed. smcu insulated by its typeof check.
T4 tbut portability open

bytesToUtf8(DataView): TextDecoder decodes it, the JS fallback returns ""

Runtimes: TextDecoder ✔ correct · no-TextEncoder ✔ but empty
Both 'succeed', but with different results - worse than an error difference. smcu never passes a DataView.
T5 tbut robustness open

Silent coercion of wrong types, the same on every runtime

Runtimes: uniform
toU8 = x instanceof Uint8Array ? x : new Uint8Array(x): DataView → "" / 0n, string or null → "", detached → "" (bytesToUtf8, bytesToUvy), uvyToBytes(number) → empty. Root cause of T1-T4 too: tbut validates content, never type.

Proposed for thingy-byte-utils (T1-T5)

One type check per entry point, before any branch: strings must be typeof "string", bytes instanceof Uint8Array (or explicitly also ArrayBuffer), else TypeError. That removes the root cause of all five, costs one typeof/instanceof per call (not measurable next to the conversion), and keeps "validates content" plus "validates type". It would also let smcu drop its own wrapper checks. Detached arrays would then throw on the JS path too if toU8 checks bytes.buffer.detached.
