Security: small-order points

Ed25519 has 8 "small-order" points (identity, order 2, 4, 8). Multiplying one by a clamped secret scalar always lands on a public, known point. Nothing in our API rejects them.

critical

F1 · A small-order public key makes verify accept any message

noble 3 verifyAsync defaults to zip215: true (cofactored, permissive). With A = identity, R = identity, S = 0 the check passes for every content:

verifyHex("01"+"00"*31 + "00"*32, "01"+"00"*31, "transfer all funds")
true

Impact: any system where users register their own public keys can be given a key that "signs" everything. Fix: strict RFC 8032 mode, which also rejects non-canonical encodings. index.js:77

high

F2 · Encrypting to a small-order key gives no secrecy

diffieHellmanSecretRawHex(anySecret, identity | order2Point)
"0100000000…00"   // same for every secret key
asymmetricEncryptHex("secret", identity)
succeeds, AES key = sha512(0100…00), public

Impact: a corrupted, zeroed or malicious recipient key turns encryption into plaintext, silently. A crafted referencePoint on decrypt does the same: anyone can build a ciphertext that "decrypts" for every recipient. Fix: one helper, used by the two functions every path goes through, diffieHellmanSecretRawBytes and elGamalSecretRawBytes.

Correctness

medium

F3 · KDF accepts an empty salt

deriveSymKeyFromPassword("pw", "") succeeds. Without a salt, one precomputation cracks every user's password at once. Fix: throw RangeError when the salt is shorter than 16 bytes. The minimum iteration count stays the caller's choice.

medium

F4 · Lone surrogates are silently replaced

encrypt("a\uD800b") decrypts to "a�b", so what comes back differs from what went in, with no error. Fix: in padContent and createSignatureBytes, throw TypeError unless typeof content == "string" && content.isWellFormed() (available from Node 20, matching our engines field). The TypeError also gives a clearer message for non-string content.

H1 unpadContent: end < 1 is false for NaN, which an empty plaintext produces. Today V1_MIN_LENGTH prevents that, but only by accident. Write !(end >= 1) instead (index.js:144). One character's worth of change, and the check holds on its own.
H2 The legacy CBC fallback leaks success or failure plus timing (padding check vs. salt check), so it's a possible padding oracle on old ciphertexts if a server decrypts input an attacker controls. In my run, 0 of 3000 random 64-byte inputs got through the fallback. Same family as the risk we accepted in D5. Document it in Step 5 and re-encrypt old secrets soon.
H3 The asymmetric key is sha512(lB), with no binding to A or B. GCM is not key-committing. Fixing either breaks v0.3.1 compatibility, so document both in the README.
H4 I ran the suite on node only this round. bun and deno are untested. Run all three after the fixes.
