Attacks

criticalconfirmed

S1 · Tampered legacy ciphertext decrypts without complaint

symmetricDecrypt silently falls back to the legacy AES-CBC format, and that format has no integrity check. unsaltContent only checks the first and last bytes, so its "nobody has tampered" comment is false. I flipped bytes in block 30 of a v0.3.1 fixture:

g[30*16 + i] ^= "x" ^ "PWNED!"[i];  symmetricDecryptBytes(g, key)
"…xxxxx֊G'}\"�\t�2t�q�PWNED!xxxx…"   // no error

Impact: v1 GCM is only as strong as the weakest format that decrypt accepts. Any legacy ciphertext under a key can be edited (one block gets garbled, the next one is attacker-chosen). This also applies to asymmetricDecrypt. It reopens the auto-detect decision from 2026-10-28, which didn't know about this.

Which way?

A and B also get rid of S3 (one AES key shared by CBC and GCM) and the fallback coupling in the bit-flip test.

mediumconfirmed

S2 · Mixed-order points leak 3 bits of the secret scalar

publicPoint rejects pure small-order points but accepts B + T8. The scalar is reduced mod L, so the term (k mod 8)·T8 survives. An attacker sends referencePoint = A + T8 and learns k mod 8 by watching which of 8 decryptions succeeds.

diffieHellmanSecretRawHex(bob, alicePub + T8)   // accepted
attacker learns k mod 8 = 4   (actual: 4)

Fix: one line in publicPoint. Honest keys are torsion-free, so the v0.3.1 fixtures still pass.

if (P.isSmallOrder()) throw …
if (P.isSmallOrder() || !P.isTorsionFree()) throw …

Design gaps

medium

D1 · Ciphertexts can be swapped between records

Nothing ties a ciphertext to where it belongs. In a secret manager, user A's token moved into user B's slot (same key) decrypts fine. GCM supports this natively through additionalData.

Fix: an optional context string on symmetric and asymmetric encrypt/decrypt, passed as AAD. Leaving it empty behaves exactly as today. It is an additive API change, best done before publishing because it changes the v1 contract.

mediumconfirmed

D2 · KDF promises PIN protection; iterations unbounded

  • A 4-digit PIN is 10⁴ × 600k SHA-256 operations, which a GPU brute-forces offline in seconds. The comment and README saying "passwords, PINs" mislead.
  • iterations = 1 is accepted. If {saltHex, iterations} is stored where an attacker can write, they can force a downgrade, or a denial of service with 10⁹.

Fix: remove "PINs" from the docs and enforce, for example, 100k ≤ iterations ≤ 10M.

low

D3 · What decrypt and verify do not prove

  • asymmetricDecrypt succeeding only means that someone encrypted to Bob. Developers will read it as "Alice sent this."
  • Signatures carry no context, so a signature over "true" in protocol X is also valid in protocol Y.
  • diffieHellmanSecretHash defaults to an empty context, so every use case gets the same key.

Proposal: a README section called "What this does not guarantee". No code change.

Developer traps

highconfirmed

T1 · Forgetting await makes every signature valid

if (verify(garbageSig, key, msg)) grantAccess()
Promise is truthy → access granted

This is the most likely real-world failure. createSymKey* is the only sync function, which teaches developers that some calls don't need await.

Fix: make createSymKey* async so every function is async, and put a bold README warning plus the @typescript-eslint/no-floating-promises hint.

mediumconfirmed

T2 · The Hex/Bytes suffix means three things

FunctionSuffix refers toTrap

Proposal: renaming is out of scope (aliases need to keep working). Document the convention in one table in the README and the .d.ts.

mediumconfirmed

T3 · One public key, many string identities

"D49E…" and "d49e…" verify the same signatures but compare as different strings. Apps that use publicKeyHex as an identity (allowlists, user lookup) can be tricked into creating duplicates or missing an entry when checking.

  • a) Accept lowercase only and reject uppercase. That is strict, and possibly breaks callers who pass uppercase today.
  • b) Keep accepting both and document "compare keys lowercased or as bytes". All outputs are already lowercase.

Minor, no decision needed (FYI)

• S3 One AES key is used for both CBC and GCM, and the legacy IV is fixed at key[0..16]. This goes away with S1 A or B.

• Random padding only hides lengths up to 255 bytes. Mention it in the README.

• The catch-all in decrypt hides programming errors (wrong types become "Decryption failed!"). See X5.

• There are 30 aliases, each one more name to audit. Kept for compatibility.

• The signing key is also used for DH and encryption. That is defensible, but should be a documented choice.
